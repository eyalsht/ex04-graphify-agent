# Known Limitations

This file is an honest, defensible self-assessment of EX04 (Graphify + Obsidian
Reverse-Engineering Agent), as required by **R8.9** (Known limitations + honest
self-grade) and the `CLAUDE.md` non-negotiable: *"Honest self-grade with
`docs/KNOWN_LIMITATIONS.md`; conservative, defensible number."*

98% coverage, all files ≤150 lines), the keyless and keyed token runs are committed, and the
graph-guided route is the three-agent crew of ADR-0006.

2. **`docs/ASSIGNMENT.md` extraction caveat.** The source PDF
   (`lec/ex04-gaphify-obcidian-Reverse-engineering.pdf`) embeds its Hebrew body text with a
   custom font encoding that standard extractors (`pypdf`, etc.) cannot decode into

   reader) to catch any misreadings; corrections that change scope should be filed as ADR
   amendments.

3. **Multi-agent crew: realized as LangGraph subgraphs, and the "GitHub agent" is scoped to
   navigation.** The lecture (§11.1.4) asks, as the preferred design, for three specialist
   agents (GitHub/clone, graph-analysis, refactor). We deliver exactly three —
   **Navigator** / **Analyst** / **Fixer** — as composed LangGraph subgraphs rather than a CrewAI
   crew, to keep every LLM call individually attributable for the R5.6 token comparison
   (ADR-0006). Two honest caveats: (a) the target repo is **vendored** and the Graphify artifacts
   are **committed** baselines (CLAUDE.md §4), so the Navigator *loads and navigates* the committed
   target + map rather than cloning from GitHub at runtime — named **Navigator**, not a live
   "GitHub agent"; (b) the orchestrating supervisor is **deterministic** (rule-based routing, no LLM
   supervisor call), a deliberate choice that preserves token parity with the naive baseline.

4. **Refactor loop is bounded to the bug-localization scale, not an architectural re-graph loop.**
   The lecture's refactor loop (§11.1.5) envisions: apply a fix → re-run Graphify → re-evaluate the
   new graph → repeat until an architectural-quality bar. On this **76-line, single-bug** target
   that per-iteration re-graph would be noise (the lecture itself calls re-running Graphify
   "pointless on a small project"). We therefore implement the loop as the bounded
   `validate → hypothesize` search **inside the Analyst agent** (stop condition:
   `max_findings_tried`, config-driven) plus a **one-shot** before/after Graphify re-graph done
   once after the fix (`artifacts/graphify_post_fix/`, `reports/graph_diff.md`). This is a
   deliberate scoping of the loop to the target's size, not an oversight; a larger codebase would
   warrant the full iterative re-graph loop. Unit tests gate every change at the suite level (244
   tests), rather than the agent re-running them inside each loop iteration.

5. **`hot.md` generated (Phase 4) — ranking composition note.** `obsidian/hot.md` is now
   generated by `ObsidianWriter.write_hot_md()` (degree DESC, betweenness DESC, id ASC;
   R5.1.4/R5.6.1), with the metric disclosed in the file. With the configured
   `hot_md_top_k = 8`, entry #1 is `Polygon` (degree 4, community 4 — the bug location) as
   required, but entries #2-8 span communities 0/2/4 (not exclusively the polygons
   community) because `mathsquiz_readme_maths_quiz` (degree 3) and several degree-2 nodes
   outrank the remaining polygons-community nodes under this disclosed, non-arbitrary
   metric. `license_mit_license` (degree 1, the isolated node) legitimately appears at
   rank 7 of 8 — not artificially excluded, consistent with "unless k is large". This is
   reported honestly rather than tuning the metric to force an "all polygons" outcome that
   the real graph data does not support.

6. **Token-comparison: keyless + keyed layers BOTH done (Phase 8) — one-sample, tier-bound
   caveat.** The keyless *input-context* reduction (R4.1) is committed: **76.7%** (graph-guided

   with graph-guided reaching the correct fix while the naive dump did not (R5.6.2/R5.6.4/R7.8/
   R4.2). Numbers trace to committed gatekeeper ledgers (`artifacts/runs/*.jsonl`); cost =
   logged tokens × the config-driven `pricing`. **Caveats (honest):** (a) it is **one** live
   run, not a multi-seed benchmark; (b) the stronger Gemini **Pro** tier was **unavailable on
   the free key** (quota = 0), so the result reflects `gemini-2.5-flash` specifically — not the
   best model available on a paid tier; (c) reaching a clean pass required two provider-quirk
   fixes (a spurious `function_call` dropping the patch text; markdown-fenced output), both
   absorbed in the provider adapter + the agent's output seam and disclosed in

9. **`draw_polygon`'s `turtle` dependency.** The `turtle` module requires a display/GUI
   environment, which is unavailable in CI or headless test runs. Per
   `docs/PRD_token_comparison.md`, the correctness check for the fixed `draw_polygon` will
   use a mocked call-count assertion (verifying the right sequence of `forward`/`right`
   calls for arbitrary `sides`) rather than a visual/rendered verification.

10. **Enforced branch protection needs a public repo or GitHub Pro.** The repo is **private**
   (to keep student IDs unindexed). GitHub gates branch-protection rules / rulesets behind
   Pro for private repos (HTTP 403 on the free tier), so server-side *block-until-CI-green*
   cannot be enforced here. Mitigations in place: CI (`.github/workflows/ci.yml`) runs
   ruff + mypy + pytest (≥90%) + the structural evals + the three gate scripts on **every
   push and pull request** to `main` (verified green on the initial push); a PR template
   enforces the checklist; and local pre-commit hooks run the same gates. To turn on
   enforced protection the moment the repo goes public (R7.1, at submission) or onto Pro,
   run `bash scripts/enable_branch_protection.sh` (a one-command ruleset that requires a PR
   + the `quality` check and blocks force-push/deletion).
